# Object types (client-defined; the server stores a number)

Every object is one protobuf message of its type (`01-architecture.md`, "Values and
conflicts"). Common fields on every type: `author` (user id), `authored_at`, `edited_at`.
Ordering of lists is a `pos` fractional index on the item. A file reference is `{ slot, sha256,
size, content_key }` inside the message; the bucket key is derived from the object id and the
slot, and the server never sees the reference. A thumbnail is not a file: it is a `bytes` field
inside the message, at most 64 KiB, generated by the uploader at a fixed size, so it travels with
the object, a holder of the object always has the grid, and it never expires (round 14). Numbers
are spaced by tens per feature area; a breaking change takes the next free number in its block.

Derived on the client, never stored: balances, poll tallies, the calendar (events plus member
birthdays), unread counts, sort orders, and the timeline. Deleting a parent is the client's
cascade (`01-architecture.md`): deleting a post pushes tombstones for its photos and comments in
the same batch. The parent id is a field of the child, inside the ciphertext.

## The timeline is the log, rendered

There is no `activity` type. The object log already records every change in group order with
its author and time inside the document, so the timeline is a projection of it:

1. **Classify.** An object the device had not seen is a create, a known one with a newer
   `edited_at` is an edit, a tombstone a delete. Type and parent name the event: a `photo` under an `album` is "added a photo to <album>", a `message`
   under a `message` is "replied in a thread", a `todo_item` whose `done` flipped is "ticked off
   <text>", an `expense` create is "added <amount> for <description>", a `poll` create is
   "started a poll", a `vote` is "voted".
2. **Collapse.** Same author, same event kind, same parent, within one hour fold into one entry
   ("Anna added 12 photos to Summer"; a `note_update` child is "edited <note>", one entry per
   author per hour). Deletes are hidden by default (a tombstone carries no plaintext to describe
   anyway).
3. **Interleave** with `post` entries, sorted by `authored_at` / `edited_at`, newest first.
4. **Filter** per group by event kind (client preference). Activity in a subgroup appears in the
   parent's timeline for members of that subgroup only, since nobody else holds its key.

Scrolling back past what the device holds asks a member device for the older range
(`RequestHistoryRequest`, `02-ledger.md`), so the feed fills across types in `seq` order. The
same classification produces the local notification text after a silent push; the server never
knows what happened.

## Merge strategy per type

Three strategies, none on the server (`01-architecture.md`, "Values and conflicts"):

- **rebase** (default): re-apply the changed fields, and for repeated fields the added or removed
  elements, onto the current row; the same field or element changed on both sides goes to the
  later push; a returned tombstone ends the edit; an invalid result is shown, not pushed.
- **append-only**: never edited after creation, so never in conflict; only deletion touches it.
- **per-user singleton**: id = UUIDv5(target, user), one object per user, only its owner writes;
  conflicts exist only between that user's own devices and the later push wins.

| Type | Strategy | What can conflict |
|---|---|---|
| group_profile | rebase, singleton per group | two admins at once, field by field |
| member_profile | rebase, singleton per user | the user's own devices |
| invite_secret | append-only | nothing |
| post, comment, message | rebase | the author's own devices; others only add children |
| photo | rebase | caption; files are immutable by hash |
| album | rebase | title, cover |
| reaction, vote | per-user singleton | the user's own devices |
| todo_list | rebase | title |
| todo_item | rebase | `done` is a boolean (tick vs untick: later wins); `pos` is a field, so a move cannot duplicate |
| note | rebase for `title`; body is append-only `note_update` children combined by `yrs` | the title only |
| note_update | append-only | nothing |
| expense | rebase, elements for participants | field by field; shares and balances are derived, so they cannot disagree with the inputs |
| settlement | append-only | nothing; undo is a delete |
| ticket_share | rebase | holder, status |
| event | rebase, validated | start and end edited apart can cross: shown to the user |
| poll | rebase, elements for options | votes are children, so an option change never fights a vote |
| venue | rebase | comments and reactions are children |

A concurrent create of the same singleton id is a conflict on `base_seq = 0`: the second device
rebases its fields onto the row that got there first.
